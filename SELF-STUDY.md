## 1. Експеримент №1: DTL та автоекранування (Auto-escaping) / Захист від XSS

### Хід експерименту:
1. Через форму або адмін-панель додано товар із шкідливою назвою, що містить JavaScript-код:
   ```html
   <script>alert(1)</script> Фільтр масла
   ```
2. Відкрито сторінку списку товарів `http://127.0.0.1:8000/products` та перевірено поведінку браузера й вихідний HTML-код («Переглянути джерело сторінки» / View Page Source).

### Результат:
- Браузер **не виконав** шкідливий JavaScript-код (спливаюче вікно `alert(1)` не з'явилося).
- У вихідному HTML-коді сторінки теги `<` та `>` були автоматично перетворені Django Template Language (DTL) на відповідні безпечні HTML-сутності (HTML entities):
  ```html
  <td class="font-weight-bold">&lt;script&gt;alert(1)&lt;/script&gt; Фільтр масла</td>
  ```

### Висновок:
Django Template Language за замовчуванням автоматично екранує всі значення змінних у контексті шаблону (`autoescape on`). Це захищає веб-застосунок від вразливостей міжсайтового скриптингу (Cross-Site Scripting, XSS), запобігаючи виконанню довільного коду зловмисника в браузерах інших користувачів. Фільтр `|safe` для неперевірених користувацьких даних ніколи не повинен використовуватись.

## 2. Експеримент №2: Поведінка статичних файлів при `DEBUG = False`

### Хід експерименту:
1. У файлі `config/settings.py` змінено значення параметру:
   ```python
   DEBUG = False
   ALLOWED_HOSTS = ['127.0.0.1', 'localhost', 'testserver']
   ```
2. Перезапущено тестовий сервер командою:
   ```bash
   python manage.py runserver
   ```
3. Відкрито сторінку `http://127.0.0.1:8000/` та перевірено підключення файлу стилів `catalog/css/style.css`.

### Результат:
- Сторінка відобразилася без стилів CSS (голий HTML-каркас).
- У вкладці *Network* (Мережа) інструментів розробника DevTools запит до `/static/catalog/css/style.css` завершився статусом помилки **404 Not Found**.

### Пояснення:
Вбудований веб-сервер розробки Django (`runserver`) автоматично роздає статичні файли лише в режимі розробки (`DEBUG = True`). Коли `DEBUG = False` (імітація production-середовища), Django вимикає обробку статики з міркувань безпеки та продуктивності, оскільки у реальному production роздачею файлів CSS, JS та зображень мають займатися спеціалізовані веб-сервери (наприклад, Nginx, Apache) або бібліотеки на кшталт WhiteNoise після виконання команди `python manage.py collectstatic`.

*(Після експерименту значення `DEBUG = True` було відновлено).*

## 3. Експеримент №3: Тестування CSRF-захисту та HTTP 403 Forbidden

### Хід експерименту:
1. У формі створення товару `catalog/templates/catalog/add_product.html` видалено тег `{% csrf_token %}`.
2. Заповнено поля форми (назва деталі, марка, номер, країна, ціна) та надіслано POST-запит натисканням кнопки «Зберегти товар».

### Результат:
Сервер відхилив запит і повернув сторінку з кодом **403 Forbidden**:
```text
Forbidden (403)
CSRF verification failed. Request aborted.
Reason given for failure:
    CSRF token missing or incorrect.
```

В інструментах DevTools:
- У Cookies браузера присутній cookie `csrftoken`.
- У тілі надісланої форми (Form Data) поле `csrfmiddlewaretoken` було відсутнє.

### Пояснення своїми словами, чому CSRF-запит було відхилено (3–5 речень):
Захист від міжсайтової підробки запитів (CSRF) у Django базується на механізмі перевірки відповідності двох ключів — значення у прихованому полі форми (`csrfmiddlewaretoken`) та секретного токена в cookie користувача (`csrftoken`). Коли надходить POST-запит, проміжне програмне забезпечення `CsrfViewMiddleware` порівнює токен із надісланої форми зі збереженим у сесії/cookie значенням. Оскільки ми видалили тег `{% csrf_token %}`, форма не містила обов'язкового одноразового підпису, тому Django розцінив цей запит як потенційну атаку від стороннього сайту та заблокував його зі статусом 403. Це гарантує, що форма була надіслана саме автентифікованим користувачем з нашого домену, а не зловмисником через прихований міжсайтовий запит.
